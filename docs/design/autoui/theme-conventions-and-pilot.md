# 树状主题约定、官方主题系列与逐应用迁移

> 状态：迁移路线 v0.2，2026-10-29；用户明确要求扩展机制之外，从 examples/ui 逐 app 改为新形式，为所有应用提供统一官方主题系列，未来供 AutoOS 默认使用。方向与迁移目标已确认，具体语法/配色及分批验收待试用收敛，不承诺未估算的完成日期。
> 关联：[Button 语义草案](button-theme-atom.md)、[数据优先模型](design-data-model.md)、[Design47](../../../../auto-lang/docs/design/47-autoui-state-design-and-feature-architecture.md)、[auto-ui/PLAN-007](../../plans/007-autoui-tree-theme-and-examples.md)。
> 当前仅设计/计划。实施仍遵守已确认的[结构收口顺序](../../../../auto-lang/docs/design/strategy/modularization-and-refactoring-strategy.md#autoui-架构重设计的切换点2026-10-28-用户决定)，不向在途重构追加新语义。归属更新：计划/当前主题设计已归 auto-ui；[示例源码搬迁](examples-ownership-and-relocation.md)也纳入同一007合同，当前尚未搬代码。

## 1. 已确认的交付方向

本轮用户补充将“官方主题系列 + examples/ui 逐应用迁移”明确为 v0.6 的主题工作目标，不再只做框架实验，也不再由小样之后决定做不做迁移。小样用于检验/修改约定和确定批次，不用于删去应用接入目标。AutoOS 独立应用按同一路线后继承接；examples 的迁移不冒称 AutoOS 已接入。

分开三种完成口径：

| 层次 | 目标 | 推荐安排 |
|---|---|---|
| 小样与首批真实应用 | 两主题、明暗、树扩展、局部隔离；Theme Lab 之外迁移 002-counter、005-login | auto-ui/PLAN-007 r3；不是只交一个新建实验窗口 |
| 官方主题与 examples 全量接入 | 公共 token/默认组件皮肤；逐目录接入窗口/面板/标准控件/排版，切换后可读、可用且业务行为保持 | 明确迁移目标；首批后按清单分批立约，不能停在框架完成或任意几个 demo |
| AutoOS 承接与扩展 | 同源官方主题包、系统默认选择与已运行 app 更新；各独立 app 真正接入 | 后继独立应用/宿主批次；不把教学源修改当作产品仓已交付 |
| 专用设计域与工具交换 | 编辑器语法主题、终端 ANSI、图表、复杂资产/字体、Figma 往返、第三方包兼容 | 公共应用界面仍须迁移；专用内容的适用 token/合法固定值逐 app 对账，工具交换单列，不影响前面目标 |

统一设计语义、控件状态、间距/尺寸/排版基准不等于每个应用必须使用相同布局或失去自己的品牌。基础外观一致也不能只给窗口涂同一个背景色。

已读取到旧语义类和主题接线的部分消费者，不能写成“旧机制完全没有进入 demos/AutoOS”。正确基线是部分采用、组织不统一、固定视觉值仍混用；新机制尚未由这些旧用法证明成立。初步来源与逐目录状态见[迁移清单](theme-migration-inventory.md)。

## 2. 试用约定

| ID | 规则 |
|---|---|
| C-01 | 主题/token 是 Auto 模块中的树状数据，用普通 use 导入；不增加路径型加载 DSL，不另造类/trait 语言。含表达式的 Auto 源码不交给静态 AtomParser 执行。 |
| C-02 | 公共 token 的路径与类型由 AutoUI 定义；Feature/app 在所属命名空间增加字段。原始调色板可不同，组件消费的公共语义键保持兼容。实际公共键须与既有 31 键对账，不能另建同义常量表。 |
| C-03 | Theme 共享 tokens/styles/components/modes 骨架；内部可有应用/Feature 扩展。通用主题不必认识所有应用字段，应用应提供扩展默认值。扩展字段按所属 Schema 校验。 |
| C-04 | extend(base, patch, ...) 是拟议普通数据合成函数：左到右，唯一命名字段递归合并、标量后胜、数组整体替换、输入只读。任意重复 Atom 子节点不能按名字盲合并；nullable 与删除分开。 |
| C-05 | tokens.radius.control 等点访问在样式字段中保存类型化槽引用；不能先复制值再宣称支持动态 token 替换。extend 与子树设计上下文必须保留引用关联，普通对象语义不被全局改变。 |
| C-06 | theme 选择主题族；modes.light/dark 只写公共部分的差异。system 是应用的选择策略，不是第三棵设计树。每次切模式从原始公共数据重建，不叠加上次解析结果。 |
| C-07 | 显式请求主题不支持的模式则拒绝；system 可回主题声明的默认模式，resolved_mode 如实报告。一个同步事件内 theme/mode 一起校验后发布。 |
| C-08 | 每个 widget 继承设计上下文；拟议 .Design 在首帧前计算本实例局部差异，theme/mode/读取的设置变化后从基准重算，无业务副作用。不能偷用首帧后的 .Init 冒充同一时序。 |
| C-09 | 局部修改影响本 widget 及默认继承的后代，不影响父级/兄弟/另一实例；子级改同路径进一步覆盖，换主题建立新基准，不隐式携带旧主题私有字段。 |
| C-10 | 合成公共数据→选模式→继承局部差异→本实例差异→解析引用→组件状态。组件字段的直接字面值解除该字段的 token 引用，不存在 token/theme 两种整体优先级。 |
| C-11 | 错型、未知公共键、未知局部路径、引用环等给可定位诊断；运行中失败保留旧有效子树，首次挂载失败不发布半成品。 |
| C-12 | 业务状态、输入内容和组件实例身份独立于换肤；原有 class/recipe/旧主题保留明确兼容路径，不悄悄修改未选入应用的默认外观。 |
| C-13 | 官方主题包单源维护/发行，由 AutoUI 提供公共库，demo 与 AutoOS 消费同一约定和固定版本，不把整套颜色复制进每个 app。首批候选族为 Auto（默认）与 Solarized 风格，每族含 light/dark；名称和视觉值通过首批再冻结。 |
| C-14 | 已迁移 app 默认跟随宿主的 theme/mode，独立运行回到官方默认；用户显式应用偏好才局部覆盖。不能每个 app 固定 Auto/light 而阻断统一切换，也不要求每个 app 复制设置菜单。宿主跨进程通知/持久化为 AutoOS 承接批次的显式任务。 |
| C-15 | 教学/框架示例归 auto-ui/examples/ui；同一计划先做可追溯源码归位与现行消费路径修复，再在新位置改主题。auto-lang只留定位/有限固定测试输入，AutoOS产品app留原仓，不维持两份活体示例。 |

结构示意：

```auto
use themes
use my_app.design: app_defaults

pub let MySolarized = extend(themes.Solarized, app_defaults, {
    tokens: { radius: { control: "8dp" } }
    modes: {
        light: { tokens: { my_app: { panel: "#eee8d5" } } }
        dark: { tokens: { my_app: { panel: "#073642" } } }
    }
})
```

此处类型名/extend 接入、局部事件以及跨组件传播仍须通过真实语言/UI 路径证明；没有通过前只能称草案，不以 Rust 手工构造数据替代。

## 3. 小样的固定试用面

先按同一计划将全部受管 examples/ui 从语言仓归位 auto-ui/examples/ui，完成路径中性的来源/消费者校验；再新增 Theme Lab 并在新位置逐个改造002-counter、005-login。通过实际 AutoUI 工具链运行同一份 Auto 源码的 Vue 与 VM/Iced 路径；AutoOS 产品源码不在首批直接改写：

- 两个官方候选设计包：Auto 默认设计与 Solarized 风格；均有 light/dark，不声称后者严格实现完整 Solarized 标准。首批经评估后发布同源包供全部迁移批次消费，不仅为 Theme Lab 写私有配色。
- 一份主题/token 模块、一份 app 扩展；样式随 token 变化而更新。
- Button 的正常/hover/pressed/disabled/键盘焦点；Input 和 Panel 只做观察换肤与状态保留所需的最小表面。
- 同一 CapsulePanel 挂两次，其中一个有局部圆角/颜色调整；其子组件继承，一个子组件再调整。另一实例与父级不串色。
- 输入框和计数器保存业务状态；切两主题及 light/dark/system 后输入和计数保持。
- 真实切换失败案例显示可定位错误且保留旧有效主题。自动化注入系统模式变化与真实 OS 集成烟测分开记录；无系统事件证据不得声称 OS 联动通过。
- 002-counter 的增/减/重置与 005-login 的输入/必填校验在换肤后保持。两 app 消费同一官方主题来源，不能把两个原主题表各自改名后算统一。

auto-ui/PLAN-007 首批不包办全部组件/全部 app，也不包含 Feature/状态/HMR 整体改造、ACE 集成或 Figma 工具交换。其余应用迁移是已确定后续交付，不是可选推广建议。专用内容的设计值不能盲改成公共背景色，也不能据此排除整个 app 的接入。

## 4. 试用反馈与逐项推进

小样完成后按真实源码和交互评估：应用最小选择是否仅需 theme/mode；包作者是否只维护数据；添加 app token 是否需要改框架；改共享 token 是否联动；局部写入与换肤是否可预测；是否出现后端特有接线；错误是否能定位源字段。

结果允许调整约定，不把第一次可运行写法永久冻结。若普通 use/token 引用必须改动 Core 语言语义，先记录缺口并修订执行合同，不能靠字符串引用、生成器硬编码或在 demo 里手动同步变量冒充原约定。

examples/ui 先按[当前逐目录清单](theme-migration-inventory.md)推进，不局限历史发行展示名单。共享库/测试夹具单列核验，两个 031 目录不能按编号去重。后续 AutoOS 接入再从现行注册表冻结 app ID、实际来源仓/提交、后端/平台，建立与教学示例的对应表；历史 28 项展示目录不是当前分母证明。

优先消除应用外壳/通用控件中的硬编码设计值，业务专属内容另列。现有 inline/class 与新主题冲突优先级须在迁移前定清，并实际移除阻断换肤的硬编码。不能仅加一行 theme 后宣称全量接入。

首批之后按真实依赖顺序制定批次：基础控件/表单→列表/卡片/导航→复杂业务与编辑/媒体应用；批次本身允许依运行与交互依赖调整，每个 app 有独立完成状态。全部适用 app 都能选同一官方主题、运行期切换和保持业务功能，才可称 examples 全量接入。保留旧语义类但没有主题/模式统一选择、复制静态色表或只修改截图均不算完成。

如 v0.6 排期受影响，明确报告未迁移 app、原因与版本决策，不自行退回“只交实验小样”的完成口径。新功能实施仍遵守结构收口顺序，范围确认不等于提前插队授权。
