# AutoGraphics：AutoUI 式图形应用声明与组件模型

2026-10-30；目标与要求回归 v2。本文承接用户本日对 AG-001 的走读和设计纠偏，恢复最初的作者模型；不是新增实施 Plan，也不声明语法、模块装配或 ACE 集成已实现。新设计归 auto-ui，Gallery 内容归 ag-examples；历史设计与现状 Specs 仍在 auto-lang。

2026-10-30命名与局部性续议：共同组件定义采用`node`，`widget`经明确兼容迁移后退役；`view`/`view2d`/`view3d`直接声明UI/2D/3D呈现，不再嵌套`view { scene2d { ... } }`；系统事件写`on { Life.Start -> ...; Life.Tick(dt) -> ... }`，不新增辅助lifecycle节点或要求msg重复声明。`msg { Collect(Key) }`声明当前Node事件，`.Collect`及`.remaining`均指当前实例成员。默认model、呈现与on内聚，普通use复用真正组件/资源/函数；独立view导入及作用域后议，不为同组件局部引用添加重复参数映射。更新后的[示例v3与实现分析](g11-2d-target-source-sketch.md)区分已确认命名和未定运行语义；尚未实施。

2026-10-30时钟事件定名：`Life.Tick(dt)`为固定步长逻辑更新，`Life.Frame(dt)`为呈现帧节奏更新；不再使用含混的Update命名。一呈现帧可对应零次或多次Tick，多视图不重复推进同一实例。Frame仅记录为后继事件，不纳入auto-ui/016的实现、样例或验收；具体呈现调度后议，不能将Frame等同GPU直接绘制回调。本轮仍只修文档、暂不实施。

## 1. 已确认目标与适用边界

2026-10-30多屏续议：[多呈现变体与选择机制](multi-presentation-selection.md)明确每个出口从候选分支选择一个呈现，共享Node业务状态；编译期目标选择与运行时环境选择分层，保留if/#if区别。当前仅讨论默认UI、2D、3D、portrait、widget五类。具体采用view-*还是统一view内标签仍在讨论，本文早期view2d/view3d为现行草图拼写，不压过最新讨论；016不扩大到多呈现选择器。

**用 AutoUI 式的声明、组件、绑定和事件模型表达图形应用。** UI、2D、3D 扩展共同的领域语言组织方式，保留各自的布局、坐标、资源和输入语义。普通 Auto 表达式、函数、类型、模块用于逻辑；组件允许内聚地组织声明、model 和 on，也允许将复杂部分拆为外部模块再导入。Godot/Bevy 是能力与样本参考，不决定 Auto 作者接口。

依据：[Design45 §11](../../../../auto-lang/docs/design/45-autographics-wgpu-engine-and-game-prototypes.md)、[Design47 的状态/组件模型](../../../../auto-lang/docs/design/47-autoui-state-design-and-feature-architecture.md)、[CAP/CPC 长期机制](../../../../auto-lang/docs/design/46-context-profile-capability-cross-ecosystem.md)。完整 ACE/生产融合继续按原成熟度与另立实施合同推进；现在可以明确模型，不提前建设或声称完整 CPC 已可用。

当前 JSON `.agscene`、单文件 app_start/app_update、数字句柄和逐调用 credits 是有限实验 profile 的已交付接口，不是最终作者范式。保留其历史与原验收，不把支持范围外推成永久限制；不能只给旧桥套一层声明外观，就声称完成模块/组件语义。

## 2. 核心要求

| ID | 目标要求 | 设计检查方式（未来实施验收输入，当前未运行） |
|---|---|---|
| AG-A01 | 作者以具名、带类型的节点/组件声明图形应用，属性、绑定、事件与 model/on 统一组织 | 一个含两个同类型实例的图形组件，各实例有自己的状态和事件接收者 |
| AG-A02 | 普通 use 复用组件、逻辑、数据与资源定义；复杂 view/model/逻辑可独立组织 | 拆文件前后语义一致，真实模块解析/初始化/诊断生效，无源码拼接伪模块 |
| AG-A03 | 作者使用可解析的 symbol/类型化引用；持久身份与运行句柄由工具和运行时管理 | 改显示名、重排声明不串引用；缺失/错型/歧义有位置诊断，不要求手填整数 |
| AG-A04 | 模块依赖、状态所有权、场景层级、挂载/渲染图和运行存储分开建模 | 同一组件多实例隔离；同一资源可共享；多场景/多挂载不重复推进同一状态 |
| AG-A05 | 支持可复用场景定义、多场景实例及关卡/应用寿命边界 | 卸载一个实例不销毁合法共享资源/应用状态；实例状态不因同模块名而共享 |
| AG-A06 | 声明结构不固定运行存储；初期简单实现，未来可做数据导向/ECS lowering | 变换继承、绑定、事件、身份与生命周期在优化前后可观察语义保持 |
| AG-A07 | 逻辑一致性、局部故障、渲染数据发布和 GPU 呈现分别定义 | 装饰草缺资源可按策略降级；拾取关联变化按明确事务域处理；设备失效单独恢复 |
| AG-A08 | 限额按实际支持域版本化；模块化不以单文件/单 VM/一帧全世界事务为前提 | 模块拆分不凭空增额度，也不因多模块天然拒绝；旧 32credits 不冒充永久语言规则 |
| AG-A09 | 示例展示正常作者模型和完整玩法意图；低层桥只作对应版本研究样例 | 真实导入可复用组件、具名资源与事件，不靠漏处理事件/隔帧跳功能美化成本 |

“可审计 agent 代码运行时”不是已确立的 AG 产品定位，撤回作为总体目标或限制模块化的理由。错误诊断、来源复现、依赖身份和可选回放保留各自用途；有特殊执行审计需求时另设明确配置，不替代一般应用模型。

## 3. 六个细节的讨论草案

配套阅读：[G11/2d目标源码草图](g11-2d-target-source-sketch.md)以普通use与model/view/on展示拆分、具名资源和事件绑定；全部图形语法为讨论表示，未实施。

本节记录建议与待决点，不能作为已经批准的语法或实现合同。§1–2为本轮已确认方向。

### 3.1 作者声明、Atom 与持久化

建议 Auto 中的 view 类领域声明作为主要编程入口；Atom＋Schema 承载可编辑的纯数据场景/资源声明，两者消费一致的类型化领域模型。Atom 不是另一套脚本语言，不自行执行任意函数；包含表达式的绑定和事件逻辑走 Auto 语义。

JSON 是当前原型便于保存/验证的选择，没有“可审计所以只能 JSON”的要求。无需先删除旧格式；先定义数据/表达式/模块引用边界及版本映射，再决定兼容 reader、作者保存形式和构建制品。原始源码身份、语义内容身份、规范化构建制品身份分开；不要求不同排版的源码有相同原始 hash。后缀（包括 scene.as）暂不冻结。

编辑器改纯数据属性与用户改 Auto 源码的往返规则必须明确：谁是权威源、允许改哪些区域、如何保注释/源码位置、冲突如何报告。不能宣称任意可执行 Auto 能无损反编译成 Atom 或被属性面板任意改写。

### 3.2 场景与逻辑绑定

图形Node沿用 model/view/on 的职责：view/view2d/view3d声明节点与子组件，model持有本Node状态，on处理事件；属性直接绑定本实例model/computed，子组件经props/事件或明确接口协作。跨组件状态不按同名字段自动合并。

复杂且有真实复用边界的组件、纯数据、控制器/store和函数可单独导出，再普通use导入；不强迫场景与逻辑分成两个靠数字对接的工程。将同一个Node的呈现单独拆出是否需要作用域保持，暂不冻结机制；默认内聚局部引用，不能要求每次将model重新映射给MainScene。事件有实例接收者、payload和明确顺序，不默认所有逻辑进入全局app_update。运动由Life更新事件调度，不能以每帧重建整棵声明树代替。

已确定node与Life命名；不另造scene专用组件类型。待讨论：外部片段确有需要时的导出/作用域、事件端口类型、Mounted/Start/Tick/Frame的具体时序和实例寿命。本轮没有可运行新语法交付。

### 3.3 资源与节点引用

建议作者使用 symbol 和类型化资源引用；编译/装载阶段解析到内部资源键、句柄或索引，避免每帧字符串查找。区分模块符号、显示名、持久对象 ID、资源内容 hash、运行实例句柄；它们不能混成一个 id 字段。

逻辑引用重命名应由解析/工具支持；引用不能靠显示名全局搜索。静态引用在构建时检查，运行时导入则按显式装载边界解析；共享资源驻留、替换代次/失效仍需运行时管理，不能只说“编译成整数”就省去生命周期。源码不必暴露 hash，分发清单仍可用 hash 验资源。

### 3.4 多模块与多场景

代码由普通模块/包依赖图组织；场景树表达空间组合，逻辑 owner 管状态寿命，呈现/挂载与渲染依赖另有图。场景树不替代 use 图，不要求一个节点一个文件或一个 VM。源码模块、组件定义、组件实例、运行任务/VM 是不同单位。

建议寿命至少区分应用/游戏会话、关卡/世界、场景/组件实例、共享资源；只有显式共享才共享状态。切关可采用“准备下一关→成功后切换→释放旧关”，失败保留当前关；背包/进度可由上级 owner 保留，不等于每次 Stop 销毁全部 VM。加法式多场景、后台加载的具体支持分期另定。

多个执行单元可交付更新/命令后汇合；调度、读写冲突、事件顺序及取消按实际并发形态定义，不默认跨 VM 分布式事务，也不预先强制所有模块共用单一运行实例。

### 3.5 树状声明与 ECS 执行

接受“作者组织与执行存储解耦”的方向：树状节点/组件声明→受检领域模型→执行计划/存储。初期保留简单实例和层级数据即可；未来可按组件布局、访问集合、批处理和系统调度重组同类数据，不要求作者重写成低层 ECS。

空间父子仍需明确关系/变换系统；owner、事件接收者、绑定依赖及对象身份不能因数组重排丢失。ECS 是可选运行策略，不等于自动并行，也不能任意重排有副作用逻辑。未来优化需有来源映射和语义对照；本轮不引入 ECS 库或修改 renderer。

### 3.6 现有示例演进

建议以 G11/2d 做首个新作者模型纵向样例：关卡根组合 Player、三个 Coin、Hazard、Goal 和 HUD；用具名资源/节点引用，Player 负责控制，Coin 发送一次收集事件，关卡 model/on 管计数与胜负，Hazard 独立更新。两份同类型实例验证隔离；共享定义跨文件 use；原 main-alt 的行为敏感性保留为参数或合法逻辑变化。

这只是检验模型的建议，不是新示例或旧 G11 已改写。先冻结最小语义/编译与执行路径，再在 auto-ui 计划实现引擎能力；ag-examples 后继独立消费真实交付，验证新旧玩法、图像、输入、事件与重开。新能力发布前，不在 Gallery 伪造转译器或用 Rust 补玩法。

旧锁/源码/验收先作为 legacy 实验基线保留；显式版本升级后逐项迁移，不批量覆盖旧证明，也不把所有历史格式永久兼容变成默认承诺。当前在途 Plan 的 AC 不被本文扩大或删除，是否改线另由具体指令与修订决定。

## 4. 故障与发布的准确边界

拾取等关联操作可在同一受控状态域采用事务；同步通知批处理不自动等于失败回滚。装饰资源失败可占位/跳过，关键关卡准备失败可取消切关，组件异常可局部隔离；哪些变化必须共同生效由领域不变量确定。外部声音/文件/网络效果不能承诺撤回，必要时提交后执行或补偿。

渲染器需要有效、同步且寿命正确的输入；最终呈现由合成路径协调。一个呈现目标不要求单文件/单模块/单场景/单 VM；实际 GPU swapchain 可多缓冲，也可存在多个离屏目标。双缓冲管理生产/消费和呈现，不自动提供游戏事务，更不构成审计或禁 use 的依据。原型现行整 tick 拒绝/保 last-good 保持原版本事实，不能直接作为所有未来组件的故障策略。
