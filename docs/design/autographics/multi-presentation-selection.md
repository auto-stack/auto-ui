# Node 多呈现变体与编译期／运行时选择

2026-10-30，设计讨论 v3；依据用户本日对多屏应用、if/#if及view选择分支的澄清。仅文档，不代表现行解析器或任何平台已支持；不新增Plan、不实施。共同入口见[声明与组件模型](declarative-authoring-model.md)。

## 1. 目标与最新语义

让同一个Auto程序运行在不同屏幕：Node共享业务model、msg和on，不同呈现版本使用同一实例接收者；每个挂载出口拥有自己的环境、选中分支和呈现局部状态。桌面窗口、小组件和竖屏可同时挂载同一Node，但不会因此重复推进Life.Tick或复制业务model。焦点、滚动等局部呈现状态不强制共享。

**普通view保留为正常UI内容树；呈现选择发生在Node直属的多个呈现定义之间。** UI内部可以同时嵌入view-2d和view-3d区域，二者是组合关系，不互斥。无论直属还是嵌入，统一采用这两个名称，不另引入场景包装名。跨领域边界负责视口、相机、坐标/输入映射和资源寿命；更复杂世界表面/覆盖组合仍需明确接口。

## 2. 本轮只讨论五种呈现

| 变体 | 选择含义 | 与现状的区别 |
|---|---|---|
| 默认UI | 普通UI的默认展示 | 不自动代表2D/3D的兼容实现 |
| 2D | 被请求的二维呈现出口 | 不能仅因设备有GPU便自动选择 |
| 3D | 被请求的三维呈现出口 | 不能仅因缺UI就隐式转成3D |
| portrait | 当前出口可用逻辑高度大于宽度时的UI展示 | 是屏幕方向，非竖向布局容器；方形走默认 |
| widget | 宿主指定桌面小组件用途的UI展示 | 用途由宿主声明，不靠窗口小就推断 |

手表、MCU专用、VR专用及任意复合变体均为以后扩展，不加入本轮命名集合或016。MCU等目标的编译期裁剪机制可以先在设计中定义，不宣称平台可用。

名称已按用户确认统一为：`view`、`view-2d`、`view-3d`、`view-portrait`、`view-widget`。竖屏采用portrait，表示可用逻辑空间的方向，不是竖向布局容器。

- Node直属的view/view-2d/view-3d是对应领域的呈现定义；view-portrait/view-widget是UI呈现变体。
- 普通view内容树中的view-2d/view-3d是在当前位置创建的二维/三维呈现区域，参与父级布局与组合，可同时显示。
- 嵌入区域不因进入另一个呈现领域就隐式创建另一份业务model或重复Life.Tick；显式子Node实例化仍遵守组件实例语义。
- view-portrait/view-widget当前只定义为Node直属UI变体，不把它们扩展成容器内布局节点。
- 编译器按声明位置区分呈现定义与嵌入区域；同一直属选择键重复需诊断，内部多个同域区域则可合法存在。旧版把普通view当选择表的说法撤回，历史留Git，不新增default包装层。

以下展示目标结构，尚未实现：

```auto
node App {
    model { ... }

    view {
        row {
            view-2d { ... }
            view-3d { ... }
        }
    }

    view-portrait {
        col {
            view-2d { ... }
            view-3d { ... }
        }
    }

    on { ... }
}
```

横/竖两个呈现定义是选择关系；任一选中定义内的2D/3D视口是组合关系。view-2d/view-3d视口可以各自实例化内容，也可以显式引用同一世界的不同呈现出口；不能仅凭两个视口就推断复制或共享业务状态。

## 3. 默认选择顺序与组合条件

以下优先级作用于Node的呈现定义，不作用于view内部的UI/view-2d/view-3d内容组合。先按调用方所需呈现领域筛选，再在该领域内选择，不能把跨领域fallback隐藏在优先级中：

| 当前出口请求 | 候选顺序 |
|---|---|
| 普通UI、小组件用途、竖屏 | widget → portrait → 默认UI |
| 普通UI、小组件用途、横屏或方形 | widget → 默认UI |
| 普通UI、非小组件、竖屏 | portrait → 默认UI |
| 普通UI、非小组件、横屏或方形 | 默认UI |
| 二维呈现 | 2D分支 |
| 三维呈现 | 3D分支 |

因此“小组件且竖屏”是两个环境条件同时成立时的确定选择，不是同时挂载widget和portrait；存在widget版本时优先它，缺失再尝试适用的portrait，最后默认UI。规则由共同选择器承担，不要求每个App手写同样的if链。资源/能力不兼容的候选先排除，不能用优先级绕过构建错误或平台限制。

2D/3D领域由调用方的出口意图和已定义呈现接口确定，不由硬件能力猜测。如果没有可推断的领域且存在歧义，应诊断要求明确意图。请求3D但没有可用3D分支，不自动拿portrait/UI代替；以后若需要跨领域降级，另有显式兼容声明和支持承诺。

选择条件具有明确维度：领域、宿主用途、视口方向和目标能力。当前只有上述五种定义，**暂不新增“2D竖屏”“小组件竖屏”等交叉标签或选择器语法**。未来复合条件若开放，以条件合取表达更具体变体；须定义具体度、显式优先级/冲突诊断，不能按文件声明顺序或标签排列顺序猜结果。尚未实现的复合系统不成为016前置。

## 4. 编译期选择与运行时选择

普通if保持运行时条件语义，#if保持Auto既有编译期条件语义。这里是编译器对呈现声明的专门选择/lowering，不是将普通if提前执行，也不增加第三套可执行表达式语言。

1. 构建配置固定目标能力、允许的呈现领域/用途以及确实固定的屏幕参数。共同选择器据此保留可达变体，按已有条件编译/构建机制排除不适用定义。
2. 只计算保留变体及共同model/on所需的实际代码、资源和依赖闭包。某资源若也被共同逻辑使用，就不能随某个view删掉。未选择分支的检查和条件导入边界须沿统一编译合同确定，不承诺“未选就允许任意非法源码”。
3. 未被构建配置固定的尺寸/方向/用途在具体呈现出口运行时选择；只保留仍可能命中的分支。环境变化触发重新选择，不需每帧全树重建或重复读取全部条件。

对于固定目标，相关分支排除应是构建保证并能从目标产物/资源清单验证，不只寄希望于普通死代码优化。#if仍可供确有需要的目标专属声明/导入使用；大多数App不重复编写平台选择链。Context/Screen值能否作为编译期条件须由既有语言/构建接口明确，不把运行时对象访问直接塞进#if。

## 5. 回退、实例寿命与错误

缺专用UI版本按§3回退，不要求每个Node定义五种呈现。没有兼容候选时，构建期能确定则报错；运行期才确定则返回具名unsupported-presentation，由宿主显示错误/选择显式替代，不能悄悄空白或切到不兼容领域。零尺寸/布局尚未确定时不以0/0猜方向，可延后首次选择；已挂载内容按宿主明确的保留策略处理。

多个同类定义或相同选择键重复，必须有位置诊断，不能后声明覆盖。候选准备失败与候选不适用分开：准备失败应报告具体资源/构建错误，不自动把程序错误吞成正常fallback。可选装饰资源的局部降级仍归资源合同，不等于整个呈现选择失败。

切换呈现定义保留Node业务model/事件接收者和逻辑时钟，不重新运行Life.Start；退出的呈现挂载释放自身资源/订阅，进入版本按呈现挂载语义处理。保留同一业务状态不保证两个不同布局能自动共享焦点/滚动。多个出口的Screen/Context分别属于各自viewport，不能用全局主屏幕参数让它们相互覆盖；使用逻辑尺寸、缩放与安全区域，而非仅按物理像素/“手机”标签判断。

## 6. 与016的边界及后继验证输入

[auto-ui/016](../../plans/016-autographics-node2d-minimal-validation.md)仅等范围同步view-2d名称，仍只验证一个Player、两个独立Hazard、一个可销毁Coin，以及node/Life.Tick/use/实例状态/事件。它不实现UI/3D混合嵌套、多呈现选择器、竖屏/小组件变体、编译期分支裁剪或Life.Frame，不新增对应AC/任务/夹具；其余研究API未因统一名称而自动可用。

后继独立验证应覆盖：小组件+竖屏重叠的优先级、缺专用UI回退、错误领域拒绝、固定目标产物排除及共享依赖保留、环境切换保业务状态、多出口不同环境而Tick一次，以及一个普通UI view内同时显示2D/3D视口。这里只记录未来检查方向，不计入016，也不宣称通过。

本轮仅设计整理，未改变解析器、模型、运行入口、SDK、资源、在途实现或验收。命名讨论和逻辑规则不自动放行任何平台或生产融合工作。
